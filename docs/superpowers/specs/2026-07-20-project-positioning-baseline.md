# MobiFlow 项目定位基准

> 日期:2026-07-20
> 用途:作为后续所有开发与整改工作的**判断基准**。当遇到"这个功能要不要做 / 这个债要不要修 / 优先级多高"的分歧时,回到本文对齐。
> 状态:基于与项目负责人的场景澄清重写,取代 2026-07-08 旧版(旧版前提"仿真探索原型"已随真实研究场景校正)。

---

## 一、一句话定位

**MobiFlow 是流量采集研究的「移动端行为生成与调度引擎」。它的职责是:让 AI 可靠地、可扩展地在移动设备上制造出真实的 App 使用行为,为独立的第三方流量采集器持续喂入高价值、可对齐的流量样本。**

采集本身不在本项目范围(由独立采集器完成)。MobiFlow 解决的是采集的上游——**"高质量流量样本从哪来"**,即行为的产生、规模化与真实性。

---

## 二、研究背景与痛点(定位的由来)

负责人的研究方向是移动端设备流量采集,需要采集目标 App 使用期间产生的网络流量。产生这些流量的方式经历了演进,每一步都对应一个痛点:

1. **人工操作** → 覆盖面不足、成本高,不可取。
2. **预设场景动作链(死脚本)** → 一旦中途中断(广告页、网络问题),这次采集即无效。
3. **关键约束:采集是无人监管的** → 死脚本的中断问题被放大:事后人工核对"哪次采集有效"成本极高。
4. **目标:用 AI 增强自动化** → 提升可靠性(不中断、留证据)与覆盖面。
5. **目标:多设备调度** → (a) 并行采集不同 App,加速数据集采集;(b) 模拟设备间交互场景(互发消息、视频通话、多人群聊/会议),产出单设备造不出的关系型流量。

> **"可靠"的准确含义(负责人确认):动作链不能中断 + 有执行记录。** 核心是解决"无人值守下,这次采集到底有没有有效执行"这个判定与留证问题——而非软件测试意义上的断言正确性。

---

## 三、职责边界(重要,避免跑偏)

- **采集** 由独立第三方采集器负责,MobiFlow 不管抓包。
- **真机执行** 是执行器(`AutoA11y_Executor`)的责任边界。执行器与 Platform 之间是**数据传输 / 接口契约**关系。
  - **推论**:Agent 层与 Platform 层的开发**在仿真适配器上进行即可**,只要接口契约定清楚,能力自然落到真机。"真机能否跑"是执行器的独立工作项,**不计入 Agent/Platform 的缺口或待办**,不应作为横切关注点反复纠结。
  - 负责人此前已验证真机链路可行;当前阶段刻意先在仿真上做设计。
- **生产生命周期分工** 已定稿:Agent 负责意图/计划/正式 sequence 解析与 governed proposal；Platform 负责审批、调度、run/target/task/attempt lineage、状态与证据；Executor 负责 claim 后的 attempt 执行及 event/artifact/finish/航点证据回传。Platform attempt 不进入 Agent TaskGraph。
- **Mock Executor** 可以完整替代真机来验证上述控制面协议,包括 HMAC、nonce、pinned claim、重试和证据落库；它不运行 UI,因此通过 mock 不等于真实 App 行为已通过。

## 四、四支柱现状(均经 2026-07-20 代码核实)

| 支柱 | 含义 | 现状 | 结论 |
|------|------|------|------|
| **一 · 单设备可靠执行** | Agent 边看边决策的执行闭环,遇异常自恢复 + 留 trace | 仿真环境已有闭环(`dynamic_observe→decide_step→verify→recover` + `ExecutionTraceExporter`) | 有雏形,契约驱动可迁真机 |
| **二 · 多设备并行调度** | N 台设备并行跑不同 App,加速采集 | **平台地基已建好、能跑**:设备池、并发安全租约(`FOR UPDATE SKIP LOCKED` + 心跳续租 + `LeaseReaperJob`)、`ExperimentRun` 批量 fan-out、`/mcp` 端点、Agent 侧 `McpPlatformAdapter` 已通 | 非空白,接入采集流程即可用 |
| **三 · 设备间协同** | 两台配合(A 发 B 收 / 视频通话 / 群聊会议) | **完全空白**,全库零命中。当前 fan-out 是同构的(同一 task 下发全池),无跨设备时序原语、无角色区分 | 需新建跨设备编排子系统 |
| **四 · 细粒度动作-流量对齐** | 动作时间线供事后与流量对齐 | 执行器事件路径可**粗粒度**对齐(毫秒 epoch + `action_start/end` 双事件 + `deviceId`);目前只截动作链整体 start/end | 需补细粒度动作边界 |

### 关于 Agent 与真机操作的关系(校正旧认知)

当前 App 内的实际 UI 操作(tap/swipe/输入)由**设备端 profile 插件**执行;Agent 经 MCP 做的是创建/取消 run、发运维指令、观测状态、提治理提案。Executor 只与 Platform 的 `/executor/**` 通信并从 claim payload 取得完整任务与 attempt 身份；它不从 Agent 取得运行时 lineage。**这不是缺口,而是分层**——按第三节边界,Agent/Platform 通过接口与执行器交互,不直接碰真机 UI。用 AI 增强可靠性,是在这个接口契约之上增强决策与恢复能力,而非让 Agent 去逐像素操控真机。

## 五、差异化标尺(按"离核心价值的距离"分级)

核心价值 = **稳定、规模化、真实地产出流量样本**。三层据此用不同尺子:

### 🏆 Agent 决策层(`MobiFlow_Agent`)—— 可靠性的载体,最高标准
- 承载"不中断 + 留证据"这一最痛诉求。verify/trace 能力应服务于**"无人值守下自动判定采集是否有效并留证"**。
- 结构债优先偿还,是最可能被产品化继承的资产。

### 🔧 Platform 控制面(`AI_Mobile_Executor_Platform`)—— 调度的地基,已是关键资产
- 多设备并行的地基在此且已能跑。标尺:**契约稳定 + 调度可靠**。
- 设备间协同(支柱三)的新编排也应落在这一层(负责人明确:平台作为 MCP server 与 Agent 交互)。

### 📱 Android 执行器(`AutoA11y_Executor`)—— 责任边界内的执行落地
- 标尺:**能在真机上正确执行 Platform 下发的动作 + 产出可对齐的动作日志**。
- 细粒度动作日志(支柱四缺口)在此层补。

---

## 六、当前优先级(负责人 2026-07-20 拍板)

1. **先做多设备并行加速与调度(支柱二)**:平台地基已就绪,重点是把采集流程接上、跑通规模化并行。
2. 设备间协同(支柱三)后置——它需要全新的跨设备时序编排,比并行复杂。
3. 细粒度动作(支柱四)按需推进,服务于流量对齐精度。

---

## 七、如何使用本文档

- **选型/排优先级时**:先问"它离核心价值(稳定/规模/真实地产出样本)多近?属于哪支柱?" 再定优先级。
- **出现分歧时**:回到第一节定位 + 第三节边界 + 第五节标尺对齐。
- **边界提醒**:任何把"真机能否跑"当作 Agent/Platform 阻塞的判断,都违反第三节,应纠正。
- **场景/去向变化时**:本文档需重新评审。
