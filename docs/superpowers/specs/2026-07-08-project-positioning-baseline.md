# MobiFlow 项目定位基准

> 日期:2026-07-08
> 用途:作为后续所有整改工作的**判断基准**。当遇到"这个问题要不要修 / 优先级多高"的分歧时,回到本文对齐。
> 状态:已与项目负责人逐段确认

---

## 一、一句话定位

**MobiFlow 当前是一个研究/探索原型。其核心命题是验证:LangGraph 驱动的 Agent 能否把自然语言任务变成可靠的"动态规划 → 执行 → 校验 → 恢复"闭环。其最可能的去向是为将来产品化打基础。**

三个定位坐标(均已确认):

| 坐标 | 取值 | 含义 |
|------|------|------|
| **性质** | 研究/探索原型 | 可行性 > 整洁度;不干净是天生的、可容忍的 |
| **核心命题** | Agent 决策可靠性 | Agent 层是被验证的对象,是要守护的皇冠 |
| **去向** | 为产品化打基础 | 可维护性迟早变成硬要求,地基债要还 |

---

## 二、指导原则:定位内部的关键张力

本项目的定位组合内含一个**刻意的张力**,它是整个整改工作的立足点:

- **"探索原型"** 说的是*现在*:可行性优先,允许粗糙。
- **"为产品化打基础"** 说的是*将来*:可维护性终将成为硬约束。

因此,整改的标尺**既不是**"现在就把三层都做到生产级"(违背原型性质、浪费探索预算),**也不是**"反正是原型,什么都能忍"(会让产品化时推倒重来)。

而是这一条**总闸门**:

> ### 优先消除"会阻碍将来平滑产品化"的结构债;容忍"只是不好看、但不挡路"的脏。

一切整改优先级判断,先过这道闸门。

---

## 三、三层的差异化标尺

核心命题是 Agent 决策可靠性,去向是产品化。这两点叠加,决定三层**不能用同一把尺子**——按"离核心命题的距离"分级对待。

### 🏆 Agent 层(`MobiFlow_Agent`)—— 皇冠,最高标准

命题的载体,也是产品化时最可能被保留继承的资产。

- **标尺**:此处的结构债**优先偿还**——它既拖慢当前命题验证,又是产品化的直接地基。
- **特别升级**:分析报告中的 **A1(两套状态模型 + 有损映射)** 与 **A3(两套割裂的恢复子系统)**,在本定位下**从"技术高优先级"升级为"命题级阻塞"**。理由:状态丢失、恢复路径不明,会让"Agent 是否可靠"这个命题的**结论本身不可信**——债务直接污染了正在验证的东西。应**最先处理**。

### 🔧 Platform 层(`AI_Mobile_Executor_Platform`)—— 支撑脚手架,中等标准

服务于让 Agent 命题跑起来,本身不是被验证的对象。

- **标尺**:**契约稳定、不拖累 Agent 迭代**即可。
- **可缓**:god object(P1 `ToolFacadeService` 2493 行)——只要没挡住 Agent 对接就缓。
- **要修**:**契约漂移(P3 三重 AI 契约 / P8 前端枚举已漂移)**——因为它会让 Agent 拿到错误数据,间接污染命题验证。

### 📱 Android 层(`AutoA11y_Executor`)—— 更远的脚手架,够用即可

离核心命题最远(命题是"决策可靠",不是"真机执行可行")。

- **标尺**:**能稳定执行 Agent 下发的动作**就够用。
- **可长期容忍**:K1/K2 god class(`Engine.kt` 881 行、`TaskExecutionService.kt` 838 行)。
- **条件触发**:K3(伪插件 SPI 硬编码 `when`)——**仅当**"需要频繁新增 App 场景来喂 Agent 验证"时才值得修,否则可缓。

## 四、对既有分析报告的重加权规则

`~/Desktop/MobiFlow_设计分析报告_2026-07-08.md` 给出的是**技术严重度**排序。本基准要求:

> **用"离核心命题的距离"对技术严重度重新加权。离命题近的债优先,离命题远的债容忍。**

据此调整后的**处理顺位**:

| 顺位 | 项 | 原严重度 | 本基准判定 | 理由 |
|------|----|---------|-----------|------|
| 1 | A1 两套状态模型+有损映射 | High | **命题级阻塞** | 直接威胁"决策可靠"结论的可信度 |
| 2 | A3 两套恢复子系统 | High | **命题级阻塞** | 恢复是命题闭环的一环,路径不明则命题不成立 |
| 3 | P3/P8 契约漂移 | High/Med | **要修** | Agent 拿到错误数据 → 间接污染命题 |
| 4 | A4 适配器复制粘贴、A7/A8 等 Agent 层其余 | Med | **产品化前偿还** | 皇冠层地基债 |
| 5 | P1 ToolFacadeService god object | High | **可缓** | 不挡 Agent 对接 |
| 6 | K1/K2/K3 Android god class / 伪 SPI | High | **容忍/条件触发** | 离命题最远 |

> 注:C1(契约重复)中**跨层影响 Agent 数据正确性的部分要修**;纯 Platform/Android 内部的重复可缓。

## 五、如何使用本文档

- **整改选型时**:任一候选项,先问"它离核心命题多近?过总闸门了吗?"再定优先级。
- **出现分歧时**:回到第二节总闸门 + 第三节三层标尺对齐,而非争论技术严重度本身。
- **命题验证完成 / 去向变化时**:本文档需重新评审——尤其若去向从"产品化打基础"变为"继续快速迭代"或"阶段性交付",三层标尺会随之改变。

---

*本基准为意图对齐产物,不含实现方案。下一步若要落地整改,应基于本基准对第一梯队(A1/A3)先做一次针对性验证(确认 governed recovery 子图、`AgentRuntimeState` 的实际生产调用方),再进入实现计划。*
